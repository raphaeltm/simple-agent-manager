# Self-host multi-box step 2: a replaceable box

SAM task 01M83Q7JT5TKF63EGFMDNHMTAE, coordinator 01M7XCE59V5X0WTNF1X3NFZP5J, plan idea
01M7V5DMWTXWDMCWA5T4YC9HC5 step 2. Self-hosting only: hosted SAM (Cloudflare) is unaffected.

## Problem

A self-hosted box keeps the only copy of its sealed Worker secrets (platform keys, `secrets.env`
values, the key agent's signing key) in `.state/key-agent/bundles/` on its own disk. celld's data
(D1, Durable Objects, KV, R2, hosted git) is already durable in the fleet bucket, but without the
bundles that data is unreadable (credentials are encrypted under `ENCRYPTION_KEY`) and the box
cannot be rebuilt. Goal: a dead box can be rebuilt on a new VM from its bucket and its off-box key
alone.

## Decision: refuse replaceable mode with the `file` provider (no KEK escrow)

`SAM_REPLACEABLE_BOX=true` in `.env` turns the mode on. It requires a key held off the box
(`gcp-kms`, `aws-kms`, `azure-kv`, `transit`); `file` and `legacy-plaintext` are refused at every
seal and at `--init`'s automatic choice.

Why refuse rather than escrow: escrowing the file KEK means copying a raw root key to some other
place SAM cannot check. Put in the bucket it would make the bucket alone enough to open every
secret, which defeats sealing. Put anywhere else it is an operator process SAM cannot verify on
rebuild. A cloud key is already supported, set up once, and its use is gated by the box's own
identity. A file-key box keeps today's `verify-key-copy` path and stays non-replaceable.

impact documented. celld's own data (D1, DO, KV, R2 under `CELLD_BUCKET`, hosted git in the
`HostedGitRepo` DO) is already in the bucket: confirmed, out of scope.

## Threat model

- **Who can read the new objects.** `sam-box/` sits under `CELLD_BUCKET`, so whoever can read the
  fleet bucket reads them: the box's identity (on GCE the VM service account; on S3 the fleet key in
  `.env`), the operator, and backups. The Worker reaches the bucket only through its R2 bindings,
  which celld maps to `r2/<name>/` (`celld-config.ts`), not `sam-box/`. Agent VMs get no bucket or
  KMS credential (`agent-vm-credentials.test.ts`), unchanged.
- **Encrypted at rest with the off-box KEK.** Bundles are the existing format: AES-256-GCM under a
  fresh data key, the data key wrapped by the KMS key, header (installation id, provider, key ref)
  authenticated. The ledger is sealed the same way. Nothing new is stored in plaintext.
- **The fleet credential is the master key.** True today and unchanged: it reads and writes D1
  directly. This change adds ciphertext only, so it gives a bucket holder no new plaintext.
- **An attacker with the bucket but not the KEK** can read D1/DO data that is not encrypted by
  SAM (as today), cannot open bundles or the ledger, cannot learn platform keys or stored
  credentials. They can delete or roll back objects (as today for D1): replacing a bundle with an
  older one is detected only as far as AEAD goes (an older genuine bundle opens). Forged bundles or
  ledgers fail authentication; rebuild refuses them. Rebuild also refuses bundles with mixed
  installation ids.
- **What rebuild trusts.** The operator's `.env` (domain, bucket, provider and key reference,
  `SAM_REPLACEABLE_BOX`), the VM identity's access to the KMS key, and the checkout. It never takes
  the provider or key reference from the bucket. Bucket ciphertext is accepted only if it opens
  under that key.
- **No new trust boundary.** The box's own identity plus its KMS key, nothing else.

## Acceptance criteria

- A box with `SAM_REPLACEABLE_BOX=true` and a cloud key mirrors every bundle to the bucket.
- `SAM_REPLACEABLE_BOX=true` with `file` (explicit or automatic) is refused with a clear reason.
- `pnpm selfhost:rebuild` on a new VM restores the bundles; the next `--init`/deploy keeps the same
  installation id and platform keys.
- Live: data, sign-in, credentials, git and sealed secrets survive deleting the VM and its disk.
