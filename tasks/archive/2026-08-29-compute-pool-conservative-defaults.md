# Compute pool conservative default selection

## Problem statement

PR #1943 (`sam/compute-pools-integration`) correctly moved compute pools toward provider-native catalogs, but default pool reconciliation currently selects too broadly: every live provider catalog offering is inserted as `active` unless it inherits a disabled/deleted legacy row. On staging this can make expensive Hetzner plans selected by default after upgrade/default creation.

The intended invariant is: discover broadly, select conservatively. Default reconciliation must create catalog rows for all provider-native offerings visible from the installation/user/project credential in scope, but only active-select the concrete provider SKUs that correspond to SAM's legacy small/medium/large supported instances. Other catalog rows must be present and addable in the editor while disabled/not selected by default.

This task must open a new draft child PR against `sam/compute-pools-integration`, not `main`, and must not merge the child PR or parent PR #1943.

## Research findings

1. `apps/api/src/services/default-capacity-pool-candidates.ts:ensureCandidatesForSource()` is the risky path. It filters live/selectable provider offerings, creates deterministic concrete candidate IDs, then sets every candidate to `active` unless `legacyStatus` is disabled/deleted. This directly violates the conservative default-selection invariant.
   - Action: add a testable helper that separates existing concrete candidate status, inherited legacy migration status, and first-created non-legacy catalog rows.
2. Existing concrete candidate rows keep their status because the upsert conflict update intentionally does not update `status`.
   - Action: preserve that behavior and add explicit tests proving a user-added non-legacy offering stays active after reconciliation.
3. Legacy migration state is inferred by `legacyStatusForOffering()` from old `small|medium|large` candidate IDs generated by `legacyDefaultCandidateId()`.
   - Action: keep disabled/deleted legacy status inheritance for matching old concrete SKUs, and keep active/no-status legacy matches active on first creation.
4. The authoritative old Hetzner mappings are in `packages/providers/src/hetzner-metadata.ts:HETZNER_SIZE_CONFIGS`: `small=cx23`, `medium=cx33`, `large=cx43`. Do not infer this from price or SKU names.
   - Action: ensure live API catalog rows for `cx23`, `cx33`, and `cx43` are the only default-active Hetzner rows when present.
5. `packages/providers/src/instance-offerings.ts:getProviderInstanceOfferings()` returns static provider-native offerings with a `legacyVmSize` field for each provider. `legacyVmSizeHintForOffering()` already uses this metadata to map live provider catalog rows back to old supported SKUs by instance type/SKU.
   - Action: reuse this metadata-based mapping; do not add price heuristics.
6. `apps/api/src/services/default-capacity-pools.ts` already handles installation, user, and project credential sources and passes scope-specific provider offerings into `ensureCandidatesForSource()`.
   - Action: add tests spanning installation, user, and project default pools.
7. `apps/api/src/services/placement-resolver-capacity.ts` already filters placement through `pool.status === 'active' && source.status === 'active' && candidate.status === 'active'` in `isActiveCapacityPlacementOption()`.
   - Action: add a regression test where a disabled but resource-satisfying catalog row is ignored by scheduler/placement.
8. `apps/api/src/services/default-capacity-pool-updates.ts` activates catalog additions by candidate ID and rejects additions no longer present in the catalog. This is the explicit user-add path.
   - Action: test that explicit activation of a non-legacy offering survives future reconciliation.
9. The editor reads default pool summaries with `includeDisabled: true`, while placement reads active pools/candidates only. `readDefaultPoolSummary()` returns disabled candidate rows to the editor as long as the source is active.
   - Action: preserve full catalog visibility for editing while keeping scheduler active-only.
10. `apps/web/src/components/project-settings/ComputePoolOfferingsManager.tsx` labels disabled candidates as `Disabled`, which is technically correct but ambiguous for catalog rows disabled only because they were not selected by default.
    - Action: update available disabled offering copy to a clearer "Not selected" label if UI tests/screenshot expectations need it.
11. Existing Playwright audit `apps/web/tests/playwright/default-capacity-pools-scopes-audit.spec.ts` currently mocks 36 active candidates and expects `36 allowed · 0 removed/disabled`.
    - Action: update the audit mock to reflect the target default state: full catalog rows visible, but only legacy-supported concrete SKUs active by default; expensive offerings visible and not selected.

## Acceptance criteria

- Full provider-native offerings available from credentials at installation, user, and project scope are still discovered and tracked as catalog candidate rows.
- Default pool creation/reconciliation active-selects only concrete provider SKUs that map to the legacy SAM-supported small/medium/large offerings.
- Hetzner default selection uses metadata mappings from `HETZNER_SIZE_CONFIGS`; `cx23`, `cx33`, and `cx43` are the selected legacy SKUs when present.
- Non-legacy offerings, including expensive catalog rows, default to disabled/not selected.
- Existing explicit user-added non-legacy offerings remain active after reconciliation.
- Existing disabled/deleted/removed concrete offerings remain disabled/deleted/removed after reconciliation.
- Existing disabled/deleted legacy size rows keep the matching concrete legacy SKU disabled/deleted after migration.
- Scheduler/placement considers only active selected candidates and ignores disabled catalog-visible offerings.
- Legacy `small|medium|large` remains an internal migration/profile hint and is not exposed as a pool add choice.
- Desktop and mobile Playwright screenshots show full catalog visibility with default selected set limited to old supported SKUs, including expensive offerings visible but not selected.
- Child branch is deployed to staging; live Hetzner catalog and default-selection behavior are validated with API/D1/Playwright evidence; a real VM prompt/session provisions via an active selected offering; staging is cleaned back to zero VMs/nodes at rest.
- Draft child PR targets `sam/compute-pools-integration`, not `main`; CodeRabbit is triggered with `coderabbit-review`; neither child nor parent PR is merged.
