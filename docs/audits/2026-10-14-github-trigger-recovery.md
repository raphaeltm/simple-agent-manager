# Durable GitHub trigger recovery

The October 14 synthetic signed-ingress regression on main `faaf861ba` reproduced the code-backed risk: a routing read failed after delivery claim; the webhook returned 200; same-ID replay after the database recovered created no task. This does not establish production event loss.

The fix stores supported, signed trigger intake in D1 before ACK and processes it through the existing operational cron sweep. A processing lease and compare-and-set finalization prevent stale attempts from changing a newer claim. Per-delivery/trigger unique execution reservations, immutable admission snapshots and existing execution-derived task identities/checkpoints preserve one consequential task across partial success and interrupted submissions. Unconfirmed startup remains retryable. The same reserved-task authorization and TaskRunner idempotency boundaries remain in use.

Defaults: 256 KiB payload cap, 60-second processing lease, exponential 30-second to 15-minute backoff, 12 attempts, 25 rows per recovery/cleanup pass, a 20-second serial background processing budget checked between candidates, 24-hour pending payload expiry threshold and 90-day dedup/audit retention. All are optional Worker variables documented in `.env.example` and the environment reference; GitHub Environment overrides use `GH_TRIGGER_RECOVERY_*` names, mapped to the Worker names by the reusable deployment workflow. Completion and exhaustion erase inbox payloads; the existing execution prompt/audit retention still applies. The operational cron and GitHub trigger kill switches apply. Exhaustion is visible in `github_trigger_inbox.state`, retry/exhaustion logs, and recovery sweep counters. An already-running attempt can finish after its intake expires; expiry is not cancellation of consequential tasks.

Limits: same-ID prevention is bounded by dedup retention. Recovery cannot recover historical events whose payloads were never stored; existing pre-upgrade audit IDs remain terminal, regardless of their old decision. GitHub does not automatically redeliver a failed webhook. A storage failure before ACK or an oversized payload is therefore visible non-success, not a guarantee of eventual recovery. No GitHub-origin natural delivery or production canary proof is implied by synthetic tests or read-only health/configuration checks. No credentials, GitHub permissions, new runtime bindings, or security boundaries are added.

References: [GitHub failed webhook deliveries](https://docs.github.com/en/webhooks/using-webhooks/handling-failed-webhook-deliveries), [GitHub configuration-variable naming](https://docs.github.com/en/actions/reference/workflows-and-actions/variables), [D1 batch transactions](https://developers.cloudflare.com/d1/worker-api/d1-database/).

Operational I/O budget: expected normal candidate volume is zero (the webhook starts its durable intake immediately). Recovery selects at most 25 due rows and expiry/purge each process at most 25 rows. Task submission runs in one serial `waitUntil` loop and stops selecting additional candidates after 20 seconds; an already-running candidate can outlast that budget under existing submission timeouts. Stable execution identity and processing leases cover overlap with the next cron. Exhausted/expired intake exits the candidate set and emits existing throttled operator notifications; raw payload/error text is excluded.
