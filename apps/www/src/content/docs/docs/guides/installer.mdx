---
title: Install SAM with the installer
description: Put the SAM installer in your own Cloudflare account with one command, install SAM from the browser, finish its setup, and update it.
---

The installer puts a complete SAM in your own Cloudflare account. You run the installer in that
same account: one command puts it there, and from then on everything happens in your browser. You
sign in with Cloudflare, pick a domain, approve, and about half an hour later your SAM is live.
You need no GitHub fork and no list of secrets to copy. Your agents' machines then run on the cloud
account you connect in SAM, as with any [self-hosted](/docs/guides/self-hosting/) instance.

The installer still labels a full installation as experimental: it first shipped on 8 November 2026.

## Before you start

- A Cloudflare account with **Workers Paid** (SAM uses Cloudflare Containers, which need it).
  Cloudflare bills your account for what SAM uses.
- A domain that is active in that Cloudflare account. SAM lives at `app.` and `api.` on it, and
  each workspace gets its own `ws-…` address.
- An email address for the administrator account.
- A terminal with Git, Node.js 22.23.4 or newer (or any Node.js 24+) and pnpm 9.15.9, to put the
  installer in your account. You don't use it again after that.

You don't need GitHub to install. Where your Cloudflare account has Cloudflare Artifacts, SAM can
keep your projects' code itself; otherwise you connect GitHub after setup.

## Put the installer in your account

1. **Create a Cloudflare API token.** Open this
   [pre-filled token form](https://dash.cloudflare.com/profile/api-tokens?permissionGroupKeys=%5B%7B%22key%22%3A%22workers_scripts%22%2C%22type%22%3A%22edit%22%7D%2C%7B%22key%22%3A%22account_settings%22%2C%22type%22%3A%22read%22%7D%2C%7B%22key%22%3A%22oauth_client%22%2C%22type%22%3A%22edit%22%7D%5D&accountId=%2A&zoneId=all&name=SAM%20installer)
   and check that it lists these three account permissions, adding any that is missing:

   | Permission       | Access |
   | ---------------- | ------ |
   | Workers Scripts  | Edit   |
   | Account Settings | Read   |
   | OAuth Client     | Edit   |

   Limit **Account Resources** to the account you are installing into, give the token a short
   lifetime, and create it. This token only deploys the installer. The permissions SAM itself
   needs are approved later, when you sign in with Cloudflare.

2. **Get SAM's source at the latest release.**

   ```sh
   git clone https://github.com/raphaeltm/simple-agent-manager.git
   cd simple-agent-manager
   git checkout "$(git describe --tags --abbrev=0)"
   pnpm install --frozen-lockfile
   ```

   The installer installs exactly the version you have checked out, so it has to be a commit that
   exists in the SAM repository: a release, not local changes.

3. **Deploy the installer.** Supply the token through your shell or secret manager; do not commit
   it or paste it into an issue or chat. Your account ID is on the account's **Overview** page in
   the Cloudflare dashboard.

   ```sh
   export CLOUDFLARE_API_TOKEN
   export CLOUDFLARE_ACCOUNT_ID
   pnpm --filter @simple-agent-manager/installer run deploy
   ```

   When it finishes it prints the installer's address:

   ```txt
   Installer ready: https://sam-installer-self-hosted.<your-subdomain>.workers.dev
   ```

The command creates two things in your account (`apps/installer/scripts/deploy.mjs`): a Worker
named `sam-installer-self-hosted` on your account's `workers.dev` address, and a private Cloudflare
OAuth client for its **Sign in with Cloudflare** button, whose credentials are stored as secrets on
that Worker. Cloudflare lets only members of your account
[authorize a private client](https://developers.cloudflare.com/fundamentals/oauth/create-an-oauth-client/).
Running the command again updates the installer and keeps both.

If a Cloudflare call is refused, the command stops and names the permission the token is missing
(`ApiFailure`, `apps/installer/scripts/installer-target.mjs`). It checks that the token can read
Workers and OAuth clients before it publishes anything; a token that can read OAuth clients but not
create them fails after the installer Worker is published, and running the command again with a
corrected token finishes the job. If
your account has no `workers.dev` address yet, open **Workers & Pages** in the dashboard once to
create it, or [use your own domain](#use-your-own-domain-for-the-installer).

## Install

1. Open the address the command printed and select **Set up your cloud**, then **Sign in with
   Cloudflare**. On Cloudflare, pick the account to install into and approve the permissions.
   **What will SAM be allowed to do?** lists them first. Your password stays with Cloudflare.
2. **Choose your account.** Pick the **Cloudflare account** and the **Cloudflare domain**; the line
   below shows the address SAM will live at. To put SAM under a subdomain such as
   `sam.example.com`, open **Use a subdomain instead** and fill in **Install under**. A subdomain
   needs a Cloudflare Advanced Certificate for HTTPS; the domain itself is covered automatically.
   Enter **Your administrator email**: this is the only email that can create the first account on
   your SAM. Select **Review installation →**.
3. **Review your installation.** The summary says where SAM will live, and **What will be created**
   lists the hostnames, the address sign-in codes are emailed from (`agents.` on your domain), your
   account's `workers.dev` address, and the exact SAM version (source commit) that will be built.
   Tick the box to confirm, then select **Install SAM in my account →**.

If Cloudflare is still verifying the address SAM emails from, setup says so: try again a few
minutes later. If email couldn't be set up at all, setup asks you to choose how you'll sign in
instead, with a GitHub, Google or GitLab OAuth app whose **Client ID** and **Client secret** you
enter, then **Finish setup**. [Platform integrations after deploy](/docs/guides/self-hosting/#platform-integrations-after-deploy)
in the self-hosting guide explains how to create each app. For Google sign-in, register the redirect
address `https://api.<your domain>/api/auth/callback/google`.

**Let other people in.** An emailed code only creates the administrator's account: everyone else
needs another way to sign in the first time. Once you're in, add GitHub, Google or GitLab sign-in
in **Admin → Integrations** (see [Platform integrations after deploy](/docs/guides/self-hosting/#platform-integrations-after-deploy)),
then invite people to your projects. Signup approval is on by default (`envRequiresApproval` in
`apps/api/src/services/signup-approval.ts`), so approve them in **Admin → Users**, or turn approval
off there.

### If the review is blocked

Review stops before anything is created when something on the domain is in the way: existing DNS
records or Workers routes on the hostnames SAM needs, or no active certificate for a subdomain.
The message names what it found. Select **Use a different domain**, or remove what is in the way in
the Cloudflare dashboard and select **I've removed them — check again**. An earlier installation
you deleted can leave routes behind that block a new one on the same domain.

### If the build fails

The page says **Installation needs attention** and which stage it stopped in. Select **Retry
deployment** to resume; work that already finished is reused. **Technical details** has the error
to include if you report it.

## Come back later

The installation service is a Worker in your account named `sam-maintenance-…`, at its
`workers.dev` address. Bookmark it when you first open it; you can also find it under **Workers &
Pages** in the Cloudflare dashboard. Opening it asks for your **Recovery credential** (**Open your
installation service**).
Under **Access & recovery** you can **Replace recovery credential** (save the new one before you
confirm; the old one keeps working until then) and **Sign out**. A session lasts 24 hours.

## Update your SAM

In the installation service, select **Check for an update**. If a newer SAM release exists, **Review
your update** shows which version it would install; select **Approve and deploy this version**.
Updates only move forward to newer releases. An update changes SAM's code, not its data: it is not
a database rollback, so rolling back to an older version isn't offered.

## Remove the installer

Once your installation service is set up and you have saved its recovery credential, the installer
has done its job. Updates come from the installation service, not the installer
(`maintenance-jobs.ts`, `/update-preview`), so you can remove it:

```sh
export CLOUDFLARE_API_TOKEN
export CLOUDFLARE_ACCOUNT_ID
pnpm --filter @simple-agent-manager/installer run remove
```

This deletes the `sam-installer-self-hosted` Worker (`wrangler delete`, run by
`apps/installer/scripts/remove.mjs`); Cloudflare deletes a Worker's Durable Object storage, here
the installer's sessions, with it. Your SAM and its `sam-maintenance-…` installation service are
not touched. Then delete the API token you created for the installer. If you served the installer
on your own domain, check the domain's **Workers Routes** in the dashboard for a leftover
`install.` route.

The command leaves the installer's OAuth client in place. Without the installer Worker, which held
its only secret, the client can't be used. Setting `REMOVE_OAUTH_CLIENT=true` deletes it as well,
but we have not yet confirmed how Cloudflare then treats the access your installation received
through that client's sign-in, so leave it unless you are also removing the installation.

## Remove an installation

There is no automatic uninstall. To remove SAM, delete its Workers, storage and DNS records in the
Cloudflare dashboard, then the `sam-maintenance-…` installation service and its API tokens, and
[the installer](#remove-the-installer) with its OAuth client if you still have them. Keep any data
you want first. Leftover Workers routes block a new installation on the same domain until you
remove them.

SAM and the installation service also own Cloudflare Container applications: the installation
service's builder is one (`provision`, `apps/installer/src/provision.ts`), and SAM's own containers
are others. Check that none are left, because we have not confirmed that Cloudflare removes a
Worker's Container application together with the Worker:

```sh
npx wrangler containers list
npx wrangler containers delete <APPLICATION_ID>
```

## What the installer can access

The installer runs in your Cloudflare account, and no service operated by the SAM project is
involved. When you sign in, your installer receives a short-lived Cloudflare OAuth token with the
permissions you approve, for 15 minutes by default (`SESSION_TTL_SECONDS`), and keeps it in an
isolated session on the server side, never in the browser. With it the installer creates separate
credentials for deploying SAM, for running it, and for its build storage
(`createInstallationCredentials`, `apps/installer/src/credentials.ts`), hands them to the
installation service, and drops its own copies. Deployment permissions can cover existing Workers
in the account, not only SAM's. The installation service stores a hash of your recovery
credential, not the credential itself.

The permissions the sign-in asks for are the ones an installation needs, including Workers, KV,
R2, D1, Containers, Pages, DNS, certificates, Workers routes, Workers AI, AI Gateway, API tokens,
email sending and routing, Cloudflare Tunnel, and Cloudflare Artifacts (the full list is
`FULL_SCOPES` in `apps/installer/scripts/deploy.mjs`).

## Installer options

Set these before running the deploy command.

### Use your own domain for the installer

`BASE_DOMAIN=example.com` serves the installer at `https://install.example.com` instead of
`workers.dev`. The API token then also needs the zone permissions for Workers Custom Domains and
Workers Routes on that domain. An installer that already exists keeps its address when you deploy
again without `BASE_DOMAIN`.

An installer is not moved in place: deploying an existing one with a different address stops and
says so (`apps/installer/scripts/deploy.mjs`). To change its address, [remove it](#remove-the-installer)
with `REMOVE_OAUTH_CLIENT=true` and deploy again.

### Build everything from source

By default the installation service downloads the prebuilt parts of SAM's latest release when they
match the version being installed, checks each against the size and SHA-256 in that release's
manifest, and builds anything that is missing or different
(`scripts/deploy/installer-engine-prebuilt.ts`). The manifest comes from the same release, so this
trusts the files attached to SAM's GitHub releases in addition to the source commit you checked out.

`ARTIFACT_BASE_URL=none` turns that off, so every installation builds everything from the pinned
source. The choice is stored on the installer and stays in force when you deploy it again without
the variable; `ARTIFACT_BASE_URL=default` goes back to SAM's latest release, and
`ARTIFACT_BASE_URL=https://…` reads prebuilt parts from another location.

### Use an existing OAuth client

Set `OAUTH_CLIENT_ID` and `OAUTH_CLIENT_SECRET`. The client's name must be
`sam-installer-self-hosted` and its client URL the installer's address, or the command stops
(`prepareOAuth`, `apps/installer/scripts/deploy.mjs`). It uses Authorization Code with
`client_secret_post`, the callback `<installer address>/oauth/callback`, and every scope in
`FULL_SCOPES`; the command updates an existing client's scopes and callback to match. Do not use `workers-scripts.edit`: it is the Workers Editor role, which cannot
create the installation service Worker. Refresh tokens are not requested.

If client creation succeeds but saving its secret fails, rotate the secret in Cloudflare and supply
it through these variables before retrying.

### Bootstrap mode

`INSTALLER_MODE=bootstrap` deploys an installer that only creates an empty installation service
and cannot install SAM. An installer first deployed that way stays in that mode until you deploy it
with `INSTALLER_MODE=full`.
